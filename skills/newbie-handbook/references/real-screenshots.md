# 畫面來源規則：真圖、實拍、官方圖、示意圖（共核 · 兩個入口共用）

這份檔案是 `newbie-handbook` 的規則單一事實源，由同資料夾的 SKILL.md 引用。要改規則就改這裡一處，不要把條文抄回 SKILL.md。

「每個步驟都要有畫面」是既有鐵律，這份檔案不動那條鐵律，只管**那張畫面從哪裡來**。以前只有兩層（使用者真圖，沒有就畫 CSS 示意），現在擴成四層，中間多了兩個以前被漏掉的來源：自己用 Playwright 去把公開網頁拍下來，以及官方文件裡現成的圖。誠實標示 mock 的原則一個字都沒有改。

## 優先序：四層，由高往低挑

**優先序（由高到低，硬性順序，不是建議）**：使用者提供真圖 > Playwright 實拍公開網頁 > 官方文件圖（標註出處）> CSS 介面示意（誠實標示）。

往下掉一層之前，先確認上一層真的拿不到。「使用者沒主動給截圖」不等於「拿不到真圖」——先問一句再說。

### 第一層：使用者提供的真實截圖（鐵律：優先用）

讀者自己的畫面永遠最準：版本對、語言對、他的帳號長相對。使用者手上有截圖卻沒給，多半只是沒想到可以給。動筆前的 Grilling 就順便問一次「你手邊有沒有現成的截圖」，成品交付時再提一次「你操作時截幾張真圖給我，可以換上去」。

### 第二層：Playwright 實拍公開網頁（鐵律：教網頁工具時要拍）

教學對象是網頁工具、而且那個頁面不用登入就看得到，就自己拍。做法見下一節。這層以前不存在，是這次擴充的重點——同一套 Playwright 已經在 `assets/render.mjs` 用來出 PDF，拍圖不必再裝任何東西。

### 第三層：官方文件圖（鐵律：一定要標出處）

官方說明頁裡現成的介面圖，可以當第三順位用，但每一張都要在圖說標出處（哪個官方頁面、哪一版）。公開發布的手冊對這一層另有保守規則，見邊界 3。

### 第四層：CSS 介面示意（鐵律：誠實標示）

前三層都拿不到，才用 `assets/template.html` 的視窗元件畫示意圖。圖說一律標「介面示意」，交付時說明哪些是真圖、哪些是示意。這條是原本就有的鐵律，四層制沒有讓它變鬆。

## Playwright 實拍怎麼做

前提：教學對象是網頁工具，而且目標頁面公開、不用登入。四件事要做對。

1. **用同一套 Playwright。** 就是 `assets/render.mjs` 解析的那一套（本地或 global）。沒裝過就提示使用者 `npm i -g playwright && npx playwright install chromium`，不要偷偷改用別的截圖方式。
2. **視窗尺寸調成讀者實際會用的那個。** 教電腦版流程用桌機尺寸（`1280×800` 起跳）；教手機版網頁流程就開 mobile viewport（例如 `390×844`），讓拍出來的畫面跟讀者手上的長得一樣。尺寸選錯，讀者會在畫面上找不到你說的那顆按鈕，因為 RWD 把它收進漢堡選單了。
3. **一張圖只拍一個狀態。** 這是微步驟第 12 條的延伸：不要在同一張圖裡同時拍「按之前」和「按之後」。要對照前後就拍兩張，各自標好。
4. **檔案放專案 `assets/`，用步驟編號命名。** `assets/step-03.png`、`assets/step-03-after.png`。命名跟步驟編號綁死，改版換圖才找得到是哪一張。

最小腳本長這樣，改三個地方就能用（網址、視窗尺寸、輸出檔名）：

```js
import { chromium } from 'playwright';
const browser = await chromium.launch();
const page = await browser.newPage({ viewport: { width: 1280, height: 800 }, deviceScaleFactor: 2 });
await page.goto('https://example.com/pricing', { waitUntil: 'networkidle' });
await page.screenshot({ path: 'assets/step-03.png' });
await browser.close();
```

要拍某一區塊而不是整頁，把最後的 `page.screenshot` 換成 `await page.locator('.pricing-table').screenshot({ path: 'assets/step-03.png' })`。要整頁長截圖就加 `fullPage: true`——但長截圖在 A4 版面上會縮到看不清楚，通常拍局部比較好用。

## 四條邊界

### 邊界 1：登入牆後面的頁面，不代登入實拍

需要帳號密碼才看得到的頁面，不要自己去登入拍。兩條合法路徑：

1. 請使用者提供他自己的截圖（回到第一層）。
2. 經使用者**明確同意**後，讀他自己已經登入、已經開著的瀏覽器畫面。

這兩條的界線是「AI 代替使用者登入」與「使用者自己登入、AI 讀畫面」的差別。後者在使用者同意下是正常主路，不要因為看起來像風險就把它縮成角落註解——那正是「主次顛倒」那條常見錯誤在講的事。

### 邊界 2：手機 App 的原生畫面，Playwright 拍不到

Playwright 開的是瀏覽器，拍不到 iOS／Android 的原生 App 畫面。教手機 App 的時候不要硬湊——不要拿該 App 的網頁版冒充 App 畫面，也不要拿長得像的別的畫面代替。這種情況直接退回使用者真圖或 CSS 示意，兩者都是合格解。

判別法：那個畫面在瀏覽器打得開嗎？打不開就是原生畫面。

### 邊界 3：第三方圖片標出處；公開發布採保守原則

上網找到的第三方圖片、官方文件裡的介面圖，一律在圖說標出處。除此之外要分兩種用途：

- **內部私用手冊**（給同事、給家人、公司內部 SOP）：引用官方說明圖屬合理範圍，標好出處即可。
- **公開發布的手冊**（要放上網、要給不特定人下載）：採保守原則，優先自己用 Playwright 實拍或改畫 CSS 示意，避免版權問題。第三方圖片能不用就不用。

拿不準是哪一種，就當公開發布處理。

### 邊界 4：實拍畫面含個人資料，先遮罩再入稿

實拍或使用者提供的真圖裡如果有帳號名稱、頭像、電子郵件、電話、訂單編號、真實姓名，**先遮罩再放進手冊**。遮罩就在 HTML 裡蓋一個色塊或用 CSS 打模糊即可，不用另外開圖片編輯器。

這條對使用者自己給的截圖同樣適用——他給你的時候未必想到那份手冊之後會傳給誰。

## 與既有規則的關係

- 這是「每個步驟都要有畫面」那條鐵律的**來源擴充**，不是新增一條獨立鐵律。四層都用完還是拿不到畫面，就是那一步的敘述有問題，回頭拆步驟。
- **mock 誠實標示的原則不變**：第四層畫出來的東西一律標「介面示意」，任何情況都不能說成真截圖。
- 第二層跟微步驟第 12 條（一張示意圖只畫一個狀態）綁在一起：實拍也是一圖一狀態。
- SKILL.md 鐵律 7（成品一律不附網址或超連結）照舊：實拍用的網址只存在於你的腳本與查核紀錄，不寫進手冊的 HTML 或 PDF。
