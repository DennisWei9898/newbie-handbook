# 畫面來源規則：真圖、實拍、官方圖、示意圖（共核 · 兩個入口共用）

這份檔案是 `newbie-handbook` 的規則單一事實源，由同資料夾的 SKILL.md 引用。要改規則就改這裡一處，不要把條文抄回 SKILL.md。

「每個步驟都要有畫面」是既有鐵律，這份檔案不動那條鐵律，只管**那張畫面從哪裡來**。以前只有兩層（使用者真圖，沒有就畫 CSS 示意），現在擴成四層，中間多了兩個以前被漏掉的來源：自己用 Playwright 去把公開網頁拍下來，以及官方文件裡現成的圖。誠實標示 mock 的原則一個字都沒有改。

## 優先序：四層，由高往低挑

**優先序（由高到低，照順序挑，不是建議）**：使用者提供真圖 > Playwright 實拍公開網頁 > 官方文件圖（標註出處）> CSS 介面示意（誠實標示）。

往下掉一層之前，先確認上一層真的拿不到，或拿到的圖不能用。「不能用」只有第三層那一種例外（官方圖的語言對不上或明顯是舊版，見第三層），其他情況不算。「使用者沒主動給截圖」不等於「拿不到真圖」——先問一句再說。

### 第一層：使用者提供的真實截圖（鐵律：優先用）

讀者自己的畫面永遠最準：版本對、語言對、他的帳號長相對。使用者手上有截圖卻沒給，多半只是沒想到可以給。動筆前的 Grilling 就順便問一次「你手邊有沒有現成的截圖」，成品交付時再提一次「你操作時截幾張真圖給我，可以換上去」。

### 第二層：Playwright 實拍公開網頁（鐵律：教網頁工具時要拍）

教學對象是網頁工具、而且那個頁面不用登入就看得到，就自己拍。做法見下一節。這層以前不存在，是這次擴充的重點——同一套 Playwright 已經在 `assets/render.mjs` 用來出 PDF，拍圖不必再裝任何東西。

### 第三層：官方文件圖（鐵律：一定要標出處）

官方說明頁裡現成的介面圖，可以當第三順位用，但每一張都要在圖說標出處（哪個官方頁面、哪一版）。公開發布的手冊對這一層另有保守規則，見邊界 3。

**例外：官方圖跟讀者的畫面對不上時，不硬用。** 兩種情況算對不上：

1. **介面語言不同**：讀者用中文介面，官方圖是英文介面（或反過來）。
2. **明顯是舊版**：圖上印著舊日期、官方說明文字寫的按鈕名稱或位置跟圖上不一樣、或同一個產品別頁的圖版面已經改了。

這時候掉到第四層，照那張官方圖的位置畫 CSS 示意，圖上的字樣改用照下面「沒有實拍畫面時」那一節查到的中文。圖說照樣標「介面示意」，再加一句「位置參考官方〇〇圖（英文舊版）畫成」，〇〇寫哪個官方頁面的哪張圖。這樣讀者知道位置有依據，也不會拿一張英文舊畫面去對自己的中文畫面。

例子（2026 年 9 月第二次新手實測，步驟 15「重新啟動服務」）：當時條文寫「硬性順序」，做手冊的人就放了 Zeabur 說明頁上一張 2024 年的英文畫面（圖上印著 Created At Jan 19, 2024，按鈕是 Restart），文字卻教讀者找中文的「重新啟動服務」。照這個例外，應該畫示意，按鈕寫「重新啟動服務」，圖說寫「介面示意：位置參考 Zeabur 官方說明『編輯設定檔』頁的『重新啟動服務』圖（英文舊版）畫成」。

### 第四層：CSS 介面示意（鐵律：誠實標示）

前三層都拿不到，才用 `assets/template.html` 的視窗元件畫示意圖。圖說一律標「介面示意」，交付時說明哪些是真圖、哪些是示意。這條是原本就有的鐵律，四層制沒有讓它變鬆。

## Playwright 實拍怎麼做

前提：教學對象是網頁工具，而且目標頁面公開、不用登入。四件事要做對。

1. **用同一套 Playwright。** 就是 `assets/render.mjs` 解析的那一套（本地或 global）。沒裝過就提示使用者 `npm i -g playwright && npx playwright install chromium`，不要偷偷改用別的截圖方式。Playwright 有裝、但它自帶的瀏覽器不在（Playwright 更新過之後常見），腳本會改用電腦上的 Google Chrome，不用先下載任何東西。
2. **視窗尺寸調成讀者實際會用的那個。** 教電腦版流程用桌機尺寸（`1280×800` 起跳）；教手機版網頁流程就開 mobile viewport（例如 `390×844`），讓拍出來的畫面跟讀者手上的長得一樣。尺寸選錯，讀者會在畫面上找不到你說的那顆按鈕，因為 RWD 把它收進漢堡選單了。
3. **一張圖只拍一個狀態。** 這是微步驟第 12 條的延伸：不要在同一張圖裡同時拍「按之前」和「按之後」。要對照前後就拍兩張，各自標好。
4. **檔案放專案 `assets/`，用步驟編號命名。** `assets/step-03.png`、`assets/step-03-after.png`。命名跟步驟編號綁死，改版換圖才找得到是哪一張。

最小腳本長這樣，改三個地方就能用（網址、視窗尺寸、輸出檔名）。前半段「找 Playwright、開瀏覽器」跟 `assets/render.mjs` 是同一套做法，不要刪：只寫 `import { chromium } from 'playwright'`，Playwright 裝在全域時會找不到；全域那份用 ESM 匯入，`chromium` 放在 `mod.default` 底下。

```js
import { execSync } from 'node:child_process';
import { fileURLToPath, pathToFileURL } from 'node:url';
import { dirname, join } from 'node:path';
const here = dirname(fileURLToPath(import.meta.url));

// 找 Playwright：先本地，再全域；全域那份用 ESM 匯入時，chromium 在 mod.default 底下
let chromium;
try {
  ({ chromium } = await import('playwright'));
} catch {
  const groot = execSync('npm root -g').toString().trim();
  const mod = await import(pathToFileURL(join(groot, 'playwright', 'index.js')).href);
  chromium = mod.chromium ?? mod.default?.chromium;
}

// 開瀏覽器：自帶的執行檔不在，就改用電腦上的 Google Chrome（跟 render.mjs 同一套判斷）
let browser;
try {
  browser = await chromium.launch();
} catch (e) {
  if (!/Executable doesn't exist/i.test(String(e?.message ?? e))) throw e;
  browser = await chromium.launch({ channel: 'chrome' });
}

const page = await browser.newPage({ viewport: { width: 1280, height: 800 }, deviceScaleFactor: 2 });
await page.goto('https://example.com/pricing', { waitUntil: 'networkidle' });
await page.screenshot({ path: join(here, 'assets/step-03.png') });
await browser.close();
```

兩個瀏覽器都開不起來時，這支腳本會直接丟出錯誤；原因跟 `render.mjs` 印出的白話說明是同一件事，照那段說明處理。

**中文路徑護欄：腳本要解析自己所在的資料夾，一律用 `fileURLToPath(import.meta.url)`，不要用 `new URL(import.meta.url).pathname`。** 路徑裡只要有一個中文字，`pathname` 回傳的就是 percent-encode 過的字串，`path.resolve` 會安安靜靜生出一個名字亂碼的新資料夾，圖全部寫進去，腳本還是 exit 0，你會以為它沒跑。中文資料夾名稱在中文使用者的專案裡是常態，這顆雷實際踩過一次。

要拍某一區塊而不是整頁，把 `page.screenshot` 那一行換成 `await page.locator('.pricing-table').screenshot({ path: join(here, 'assets/step-03.png') })`。要整頁長截圖就加 `fullPage: true`——但長截圖在 A4 版面上會縮到看不清楚，通常拍局部比較好用。

**拍完先確認它在 A4 上讀得到字。** 桌機視窗尺寸拍出來的圖又寬又扁（1280×800 起跳），塞進步驟頁那個 68mm 的側邊欄會縮到只剩約 19mm 高，介面文字整片糊掉——實測過，同一張圖在側欄讀不到、跨整頁排（約 174mm 寬）就清楚。判準：**截圖裡最小的介面文字，在成品 PDF 上量起來要有 1.5mm 高**（約 4.3pt）。量不到就兩條路——跨整頁排，或者裁掉周邊只留要看的那一塊再放大。

**怎麼量**：不用印出來拿尺，用算的。

> 成品上的字高（mm）＝ 圖上文字的像素高 × 圖片在版面上的寬度（mm）÷ 圖片的像素寬

- **圖上文字的像素高**：把 PNG 放大，數最小那行介面文字一個中文字從頂到底佔幾個像素。用 Playwright 拍的圖，也可以拿「那行字的 CSS 字級 px × `deviceScaleFactor`」當近似值。
- **圖片在版面上的寬度**：看 HTML 裡放這張圖的容器寬度。模板步驟頁的側邊欄是 68mm，跨整頁約 174mm。
- **圖片的像素寬**：PNG 檔本身的寬度，不是拍攝時的視窗寬度。`deviceScaleFactor: 2` 拍 1280 寬的視窗，PNG 是 2560 像素寬。

算例：1280×800 視窗、`deviceScaleFactor: 2` 拍出 2560 像素寬的圖，最小的介面文字是 12px，在圖上約 24 像素高。放進 68mm 側邊欄：24 × 68 ÷ 2560 ≈ 0.64mm，不到 1.5mm，不合格。改成跨整頁 174mm：24 × 174 ÷ 2560 ≈ 1.63mm，合格。這就是上面那句「側欄讀不到、跨整頁就清楚」的算法。

## 介面文字以實拍畫面上的字樣為準

手上有實拍或使用者提供的真圖時，手冊裡寫的按鈕、分頁、欄位名稱，一律照**實拍畫面上真的印出來的那幾個字**；官方文件退一步，只用來確認版本與流程。官方說明頁裡的截圖常常比線上介面舊，照它抄會寫出讀者在自己畫面上找不到的按鈕名。

**程式碼層的標籤不是畫面文字。** `aria-label`、`alt`、`title` 這些是給輔助工具讀的，讀者盯著螢幕看不到它們，**不得當成介面字樣寫進手冊**。畫面上那顆按鈕如果只有圖示、沒有文字，就用形狀加位置去描述（「右邊那格的左下角，有一個喇叭形狀的小按鈕」），不要拿無障礙標籤充當它的名字——讀者會照著那幾個字在畫面上找，然後找不到。

## 沒有實拍畫面時：介面字樣先找官方繁中頁

讀者的帳號多半是繁體中文介面，畫面上的按鈕印的是中文。照英文說明頁抄按鈕名，讀者會在自己的畫面上找不到那幾個字。沒有實拍或真圖可以對照時，照這三步查：

1. **先找官方繁中說明頁。** 官方說明頁的網址後面加語言參數（Google 系列是 `hl=zh-Hant`）就會切到繁中版。同一個後台的說明常常分散在不同產品的說明中心：這一頁沒有繁中版，不代表別頁也沒有，換一個產品的說明中心再找一次。**任一官方來源（包括別的產品的說明中心）查得到逐字中文字樣，就照寫，不標待確認。**
2. **手冊寫法中英並列，中文在前。** 例如「開始使用（英文介面：GET STARTED）」。讀者不管開的是哪一種語言介面，都找得到那顆按鈕。
3. **查遍官方來源都查不到中文，就照實標出來，並補一個卡關出口。** 字樣後面標「中文介面字樣待確認」；同一步的卡關出口要寫：畫面上找不到這幾個字時，看哪個位置、靠什麼特徵認出它（例如「表單最下面、唯一有底色的那顆按鈕」）。不要自己翻一個中文按鈕名填上去，猜出來的字樣比英文原文更容易讓讀者找錯。

有實拍畫面時照上一節，以實拍為準；這三步只管沒有畫面可以對照的情況。本節最後三小節補這三步最容易判錯的地方：機器翻譯頁算不算、什麼時候才標待確認、「查無」要怎麼查才算數。

**實例（2026 年 9 月新手實測）**：一份教「在 Google Cloud 建立登入用戶端」的手冊，照 Google Cloud 的英文說明頁寫按鈕名，做手冊的人也加了繁中參數去查，但那幾頁沒有繁中版。中文字樣其實在另一個產品的說明中心：Google Workspace 遷移工具的繁中說明頁（`https://support.google.com/workspacemigrate/answer/9222992?hl=zh-Hant`，2026-09-17 開頁核對）。兩邊對起來是這樣：

| 英文介面 | 中文介面 | 手冊寫法 |
|---|---|---|
| GET STARTED | 開始使用 | 開始使用（英文介面：GET STARTED） |
| CREATE CLIENT | 建立用戶端 | 建立用戶端（英文介面：CREATE CLIENT） |
| Web application | 網頁應用程式 | 網頁應用程式（英文介面：Web application） |
| Authorized JavaScript origins | 已授權的 JavaScript 來源 | 已授權的 JavaScript 來源（英文介面：Authorized JavaScript origins） |
| NEXT | 下一步 | 下一步（英文介面：NEXT） |

手冊原本只寫了英文那一欄。讀者照著找「GET STARTED」，畫面上印的是「開始使用」，就停在那裡了。

### 機器翻譯的官方頁：可以採信，但排在人工翻譯後面

很多官方繁中說明是機器翻譯的。它還是官方來源，查到的字樣可以用；但同一個字樣有人工翻譯的官方繁中頁可以對照時，以人工翻譯那頁為準。

怎麼認出機器翻譯頁，看這兩個地方：

- **頁尾的聲明**。例如 Google 說明中心的頁尾寫「這個頁面可能含有使用 AI 技術翻譯的內容，也許會有錯誤。」各家寫法不一樣，找「AI」「機器翻譯」「自動翻譯」這類字。
- **網頁的語言標記**。在頁面原始碼最上面的 `<html lang="…">` 看語言。`zh-TW-x-mtfrom-en` 裡的 `mtfrom-en` 意思是「從英文機器翻譯過來」（Google 開發者文件與 Google Cloud 文件常見）。語言標記如果是 `en`，代表這頁根本沒翻譯，只有外框換成中文，拿它來判「中文字樣是什麼」不算數。

兩個都沒有，才當成人工翻譯的頁面。

### 什麼時候才標待確認：看有沒有一個說法站得住

- **有一個官方來源前後一致地寫出同一個中文字樣**，就照它寫，不標待確認。別頁機器翻譯自己前後不一，不算反對票；手冊的卡關出口可以順手補一句另一種譯法，讓讀者兩個字都認得。
- **同一個介面名稱，各個來源的說法對不起來，而且分不出哪個比較可信**，才標「中文介面字樣待確認」，卡關出口列出候選譯名。例如：「左邊選單的這一項可能寫成『用戶端』或『客戶』，兩個都找找看。」分不出可信度的情況，是指兩個一致的來源彼此說法不同、而且都是人工翻譯或都是機器翻譯；或者找得到的來源全都前後不一。
- 人工翻譯頁跟機器翻譯頁說法不同時，照人工翻譯頁寫，不標待確認。

例子（2026 年 9 月第二次新手實測，Google 登入設定左邊選單的 Clients）：Google 開發者文件的建立憑證頁（`https://developers.google.com/workspace/guides/create-credentials?hl=zh-tw`，語言標記 `zh-TW-x-mtfrom-en`）同一頁寫了「Clients」(用戶端) 也寫了「Clients」(客戶)，做手冊的人因此把「用戶端」標了待確認。但 Google Workspace 遷移工具的繁中說明頁（`https://support.google.com/workspacemigrate/answer/9222992?hl=zh-Hant`）操作步驟寫的是「依序點選『建立』『用戶端』『+ 建立用戶端』」，整頁一致用「用戶端」。這頁頁尾也有 AI 翻譯聲明，跟建立憑證頁同一級，但它前後一致、建立憑證頁自己前後不一，所以「用戶端」有一個站得住的說法，不該標待確認。2026-09-17 開頁核對，只算正文：建立憑證頁「(用戶端)」與「(客戶)」各 6 處；遷移工具頁「用戶端」13 處，沒有「客戶」的譯法。

### 字樣查核的方法：搜原始頁面的逐字內容，記下命中數

判斷「官方有沒有寫這個中文字樣」，照這三條做，任何一條沒做到，都不能下「查無」的結論：

1. **搜原始頁面，不看摘要。** 把頁面原始內容抓下來（例如用 `curl -sL` 存成檔，去掉 HTML 標籤），對文字逐字搜尋。網頁摘要工具會重寫、翻譯或省略內容，摘要裡沒有，不代表頁面上沒有。頁面要跑 JavaScript 才有內容、抓下來是空的，就用 Playwright 開頁再讀頁面文字。
2. **記下命中數。** 查核紀錄寫「哪個網址、搜哪個字、命中幾處、查核日期」，中文字樣和英文原文各搜一次。例如「開始使用：1 處；GET STARTED：0 處」。命中數要算在正文裡，選單、頁尾這些每頁都有的字不算。
3. **不只查一頁。** 一頁沒有，照第 1 步換別的產品說明中心再查。查過的頁面都列進紀錄，才能說「查無」。

例子（2026 年 9 月第二次新手實測，「開始使用」按鈕）：對照字樣的 agent 回報手冊的「開始使用」該標待確認，理由是它查的 Google Cloud 說明頁（`support.google.com/cloud/answer/15544987?hl=zh-Hant`）那段還是英文 GET STARTED。這頁加了 `hl=zh-Hant`，語言標記仍是 `en`，本身沒翻譯，查這頁只能證明「這頁沒有」。把 Google Workspace 遷移工具繁中說明頁的原始內容抓下來逐字搜尋：「按一下 [開始使用]」有 1 處，GET STARTED 是 0 處。手冊原本的寫法是對的，誤判來自只查了一頁沒翻譯的說明。

## 圖上加標記：後加、一張一個、圖說要聲明

實拍圖上有十幾個圖示，只用文字寫「右邊那格的左下角有一個喇叭」，讀者要掃很久。可以在圖上加記號，但照這三條走：

1. **記號一律用模板的 `.mark` 後加在圖上，不改 PNG 原檔。** `.mark` 是絕對定位的橘色框，疊在 `.shot` 容器裡的 `<img>` 上面。截圖檔案本身維持拍下來的原樣——「這是真截圖、沒有修過」這句話才站得住。用圖片編輯器把箭頭燒進 PNG，這句話就守不住了。
2. **一張圖至多標一個重點。** 兩個以上的圈，讀者不知道要先看哪一個，等於沒標。同一張圖要指兩個地方，就拆成兩步兩張圖，或者第二個地方改用文字描述。
3. **圖說必附這句聲明：橘色記號是本手冊加上去的，畫面上沒有。** 少了它，讀者會以為自己的螢幕上也該有一個橘色框，然後找不到。

座標用 Playwright 印出目標元素的 `getBoundingClientRect()` 換算成百分比，不要目測。裁切框一改，`.mark` 的百分比全部要重算，所以先把裁切定下來再標記號。

## 四條邊界

### 邊界 1：登入牆後面的頁面，不代登入實拍

需要帳號密碼才看得到的頁面，不要自己去登入拍。兩條合法路徑：

1. 請使用者提供他自己的截圖（回到第一層）。
2. 經使用者**明確同意**後，讀他自己已經登入、已經開著的瀏覽器畫面。

這兩條的界線是「AI 代替使用者登入」與「使用者自己登入、AI 讀畫面」的差別。後者在使用者同意下是正常主路，不要因為看起來像風險就把它縮成角落註解——那正是「主次顛倒」那條常見錯誤在講的事。

#### 使用者也沒走過這條路：兩階段出手冊

後台在登入牆後面，使用者自己也沒做過、拿不出截圖時，前三層畫面都拿不到，只能先畫示意。這時候不要把示意版當正式成品交出去，分兩階段：

1. **第一版是草稿版。** 畫面用 CSS 示意，封面標題旁或每頁頁尾標「草稿版」。介面字樣照「沒有實拍畫面時」那一節查，查不到的標「中文介面字樣待確認」。
2. **交付草稿版時，附一份「照做時要截哪幾張圖」清單**，請使用者拿真帳號照手冊做一遍，邊做邊截圖傳回來。清單逐步列三件事：第幾步、什麼時候截（按下去之前還是之後）、畫面要拍到哪一塊。例如「步驟 7：按『建立用戶端』之前，截整張表單」。清單第一行先提醒：畫面上出現密鑰（例如 Client secret）或個人資料時，先塗掉再傳。
3. **第二版換真圖，改標正式版。** 收到真圖後逐步換掉示意圖，並照真圖修正文字：按鈕名、欄位順序、位置描述、成功畫面，一律以真圖為準；草稿版標的「待確認」逐條清掉。每一步都換成真圖、字樣也對過，才拿掉「草稿版」改標正式版。還有步驟沒換到，就維持草稿版。

只讀手冊的人檢查不出「示意圖跟真畫面對不上」，一定要有人拿真帳號照做過，這本手冊才算驗過。

#### 使用者同意讓 AI 看他已登入的瀏覽器時

1. **AI 只截圖，不代點。** 會改動帳號設定的動作（建立、儲存、刪除、發布、切換狀態、同意條款）一律由使用者自己按。AI 在每一步做完之後截圖；要換到下一個畫面，請使用者自己點過去。
2. **截圖之前先遮蔽密鑰與個資。** 畫面上有密鑰（例如 Client secret、API 金鑰）、電子郵件、真實姓名、帳單資訊時，先請使用者把那個視窗關掉或捲開，確認畫面上看不到再拍；用 Playwright 拍的話，可以用 `page.screenshot` 的 `mask` 參數把那一塊蓋掉。密鑰一旦拍進檔案，事後在手冊裡遮罩也只遮住手冊，原始圖檔裡還是有，所以要在拍之前處理。入稿前再照邊界 4 檢查一次。

### 邊界 2：手機 App 的原生畫面，Playwright 拍不到

Playwright 開的是瀏覽器，拍不到 iOS／Android 的原生 App 畫面。教手機 App 的時候不要硬湊——不要拿該 App 的網頁版冒充 App 畫面，也不要拿長得像的別的畫面代替。這種情況直接退回使用者真圖或 CSS 示意，兩者都是合格解。

判別法：那個畫面在瀏覽器打得開嗎？打不開就是原生畫面。

### 邊界 3：第三方圖片標出處；公開發布採保守原則

上網找到的第三方圖片、官方文件裡的介面圖，一律在圖說標出處。除此之外要分兩種用途：

- **內部私用手冊**（給同事、給家人、公司內部 SOP）：引用官方說明圖屬合理範圍，標好出處即可。
- **公開發布的手冊**（要放上網、要給不特定人下載）：採保守原則，優先自己用 Playwright 實拍或改畫 CSS 示意，避免版權問題。第三方圖片能不用就不用。

拿不準是哪一種，就當公開發布處理。

### 邊界 4：實拍畫面含個人資料，先遮罩再入稿

實拍或使用者提供的真圖裡如果有帳號名稱、頭像、電子郵件、電話、訂單編號、真實姓名，**先遮罩再放進手冊**。遮罩就在 HTML 裡蓋一個色塊或用 CSS 打模糊即可，不用另外開圖片編輯器。

這條對使用者自己給的截圖同樣適用——他給你的時候未必想到那份手冊之後會傳給誰。

## 與既有規則的關係

- 這是「每個步驟都要有畫面」那條鐵律的**來源擴充**，不是新增一條獨立鐵律。四層都用完還是拿不到畫面，就是那一步的敘述有問題，回頭拆步驟。
- **mock 誠實標示的原則不變**：第四層畫出來的東西一律標「介面示意」，任何情況都不能說成真截圖。
- 第二層跟微步驟第 12 條（一張示意圖只畫一個狀態）綁在一起：實拍也是一圖一狀態。
- SKILL.md 鐵律 7（成品一律不附網址或超連結）照舊：實拍用的網址只存在於你的腳本與查核紀錄，不寫進手冊的 HTML 或 PDF。
